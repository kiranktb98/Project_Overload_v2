1 — What SSL / TLS actually does

TLS (Transport Layer Security, often still called SSL) is the protocol that encrypts the connection between Claritect's API server and your database. Without it, anyone on the same network can read the queries you run and the data that comes back.

When you connect a database source, Claritect opens a TCP connection to your database host and then performs a TLS handshake before sending any credentials. During the handshake:

  1. The database presents its certificate.
  2. Claritect checks whether it trusts the authority that signed it (the CA).
  3. If trust is established, both sides derive an encryption key and the connection proceeds securely.

Most cloud databases (Supabase, Neon, Amazon RDS, PlanetScale, Google Cloud SQL) use certificates signed by well-known public CAs that Node already trusts. This means the handshake works out of the box and you don't need to do anything extra.

2 — The three SSL modes in Claritect

Auto
Automatic (recommended)

Tries TLS first. If the server supports it, the connection is encrypted. If the server doesn't offer TLS at all, it falls back to a plain connection.

  • Works for Supabase, Neon, RDS, PlanetScale, and most cloud databases
  • Correct default for nearly everyone
  • Still validates the CA — CA errors will surface here
Require
Require TLS

Strictly requires TLS. The connection is rejected if the server does not offer it. No fallback to plain text.

  • Preferred for production databases
  • Guarantees the connection is never accidentally unencrypted
  • Also validates the CA — use a custom CA if needed
Off
Off (no encryption)

Disables TLS entirely. The connection is plain text with no encryption and no certificate verification.

  • Only for local or private dev databases
  • Should never be used for databases that hold real data
  • Use only when you control the network end-to-end
Postgres note: these modes map to sslmode values in the connection string — prefer (Auto), require (Require), and disable (Off). Claritect sets this automatically based on whichever card you pick, so you don't need to include ?sslmode=... in your connection string manually.

3 — Per-provider SSL behaviour

Provider SSL / TLS in Claritect Notes
Postgres Controlled by the Auto / Require / Off cards Auto works for all cloud Postgres (Supabase, Neon, RDS, Heroku). Use Require for strict enforcement. Use Off only for a local Postgres instance.
MySQL Controlled by the Auto / Require / Off cards Same rules as Postgres. AWS RDS MySQL and PlanetScale both work with Auto. Self-hosted MySQL without TLS configured: use Off for dev, but set up TLS before going to production.
Snowflake Always TLS — no SSL mode selector shown Snowflake enforces TLS at the platform level. All connections are encrypted with certificates signed by a public CA. No CA certificate or SSL mode configuration is needed or available.
BigQuery Always TLS — no SSL mode selector shown BigQuery communicates over HTTPS only. All traffic is encrypted and authenticated via Google's infrastructure. No SSL configuration is required.

4 — CA certificates — what they are and when you need one

A Certificate Authority (CA) is an organisation that signs database certificates. Node (and therefore Claritect) ships with a built-in list of trusted public CAs. If your database's certificate was signed by any of them, you don't need to do anything extra.

You need to supply a custom CA certificate in these situations:

Corporate proxy / SSL inspection

Your company network intercepts TLS connections — security products like Zscaler, Netskope, Cisco Umbrella, or Palo Alto do this. The proxy presents its own certificate instead of the database's certificate. Node doesn't trust the proxy's CA by default.

What you'll see: errors like "self signed certificate in certificate chain" or "UNABLE_TO_VERIFY_LEAF_SIGNATURE" even against a cloud database.

Fix: paste your corporate TLS inspection CA. See section 6.

Self-hosted / on-prem with a private CA

Your database team created their own internal CA to sign the database certificate, rather than buying one from a public CA. This is common in enterprises and banks.

What you'll see: errors like "self signed certificate" or "DEPTH_ZERO_SELF_SIGNED_CERT".

Fix: paste the internal root CA certificate your database team provides. See section 5.

You do NOT need a custom CA for: Supabase, Neon, AWS RDS, Google Cloud SQL, PlanetScale, Railway, Render, Heroku, or any database using a certificate from a public CA like Let's Encrypt, DigiCert, or Amazon Trust Services. Just pick Auto and you're done.

Where to paste the CA certificate in Claritect

In the connection form, check the box labelled "My database needs a custom CA certificate". A text area will appear. Paste the full PEM block there, including the -----BEGIN CERTIFICATE----- and -----END CERTIFICATE----- lines.

You can paste multiple certificates one after another if your chain has an intermediate CA between your root and the database certificate — just stack them in the text area.

5 — How to find and export your CA certificate

Option A — Ask your database or IT team (fastest)

If someone else manages the database, ask them: "Can you send me the root CA certificate in PEM format?" They should be able to give you a .pem or .crt file. Open it in any text editor, copy the whole block, and paste it into Claritect.

Option B — Export from Windows Certificate Manager

  1. Press Win + R, type certmgr.msc, and press Enter (for your user's certificates) — or certlm.msc for machine-level certificates.
  2. Expand Trusted Root Certification Authorities → Certificates.
  3. Look for your company name or a known TLS inspection vendor: Zscaler, Netskope, Cisco, Palo Alto, Forcepoint, or similar.
  4. Double-click the certificate to open it, then go to the Details tab.
  5. Click Copy to File…, choose Base-64 encoded X.509 (.CER), and save it.
  6. Open the saved file in Notepad and copy the entire contents.
  7. Paste it into the CA certificate field in Claritect.

Also check Intermediate Certification Authorities → Certificates if you don't find the relevant certificate under Trusted Roots.

Option C — Export from macOS Keychain Access

  1. Open Keychain Access (Spotlight → "Keychain Access").
  2. In the left column, select System or System Roots.
  3. Search for your company name or the TLS inspection vendor.
  4. Right-click the certificate → Export.
  5. Choose format Privacy Enhanced Mail (.pem) and save.
  6. Open the file in a text editor and copy the certificate block.

Option D — Fetch it from the server with OpenSSL

If you have OpenSSL installed, you can capture the chain directly:

openssl s_client -connect your-db-host.com:5432 -showcerts < /dev/null 2>/dev/null \
  | openssl x509 -outform PEM

This prints the certificate the server presents. If you are behind a corporate proxy, it will print the proxy's certificate — that is the one you need to paste into Claritect.

6 — Corporate networks and SSL inspection

Many enterprises route all outbound traffic through a security proxy (Zscaler, Netskope, Cisco Umbrella, Palo Alto NGFW, and others). These proxies perform SSL inspection: they decrypt your TLS connection, inspect the contents for threats, and then re-encrypt it — presenting their own certificate to the upstream service.

Claritect's API server sees the proxy's certificate rather than the database's certificate. Because the proxy uses an internal corporate CA that is not in Node's built-in trust list, the connection fails with a certificate verification error.

This is one of the most common SSL connection failures. If you are on a managed corporate laptop and connecting to a cloud database, assume SSL inspection is involved until proven otherwise.

How to fix it

  1. Get the corporate TLS inspection CA certificate in PEM format — ask IT, or export it from Windows/macOS using the steps in section 5.
  2. In the Claritect connection form, check "My database needs a custom CA certificate".
  3. Paste the corporate CA PEM.
  4. Leave the SSL mode on Auto or Require — do not switch to Off.
  5. Test the connection again.

Server-wide fix (for self-hosted deployments)

If you manage the Claritect API server and every connection goes through the same corporate proxy, you can trust the CA globally instead of per connection:

  1. Save the CA PEM to a file on the server, for example /etc/ssl/corporate-ca.pem.
  2. Set the environment variable: NODE_EXTRA_CA_CERTS=/etc/ssl/corporate-ca.pem
  3. Restart the API server. All outgoing TLS connections from Node will now trust this CA.
Do not set NODE_TLS_REJECT_UNAUTHORIZED=0 to work around TLS errors. This disables certificate verification entirely for all connections from that Node process — it is a serious security risk and should never be used in production.

7 — Error messages decoded

Error text What it means What to do
self signed certificate in certificate chain The certificate chain includes a certificate signed by a CA Node doesn't trust — usually a corporate TLS inspection proxy or a self-signed internal CA. Paste the corporate or internal root CA certificate in Custom CA (PEM). Keep SSL mode on Auto or Require.
DEPTH_ZERO_SELF_SIGNED_CERT The database is presenting a self-signed certificate with no CA chain at all — common with Docker-based dev databases or older self-hosted setups. For dev: switch SSL mode to Off. For production: configure a proper certificate on the database, or paste the database's own certificate as the CA.
UNABLE_TO_VERIFY_LEAF_SIGNATURE Node cannot verify the signature on the database certificate because it doesn't have the intermediate CA that signed it. Paste the missing intermediate CA certificate (or the full chain) in Custom CA (PEM).
ECONNRESET / read ECONNRESET The TCP connection was reset during the TLS handshake. Often happens when the database rejects TLS before completing the handshake. Check whether the database supports TLS at all. If connecting to a local dev database, try SSL mode Off.
certificate has expired The database's TLS certificate has passed its expiry date. The database admin needs to renew the certificate. If it is a corporate inspection CA that expired, ask IT to update the CA.
The server does not support SSL connections The database server is not configured to accept TLS. For a local or dev database: switch to SSL mode Off. For a production database: enable TLS on the server side — do not disable it on the client side.
hostname/IP does not match certificate's altnames The hostname you connected to is not listed in the certificate's Subject Alternative Names. Check the connection hostname matches exactly what the certificate covers. If connecting via an IP address, the certificate may only cover a hostname — use the hostname instead.
ENOTFOUND / ECONNREFUSED Not a TLS error — the host could not be reached at all (DNS failure or port closed). Verify the hostname and port in your connection string. Check firewall rules and whether the database allows remote connections.

8 — Quick decision guide

Use this to find the right SSL setting without reading the whole guide.

Is this a cloud database (Supabase, Neon, RDS, PlanetScale, Google Cloud SQL, Railway, Heroku)?
→ Yes: Use Auto. Done.
→ No: continue below
Is this a local or Docker-based dev database?
→ Yes: Use Off — it's not accessible from the public internet so plain text is acceptable for development.
→ No: continue below
Are you on a corporate or managed network (company laptop, office VPN)?
→ Yes and getting SSL errors on a cloud DB: SSL inspection — paste your corporate CA. Keep Auto or Require.
→ No: continue below
Is the database self-hosted and managed by your team with an internal CA?
→ Yes: Use Require + paste the internal root CA that your database team gives you.
→ No: continue below
Is the database self-hosted with a public certificate (Let's Encrypt, etc.)?
→ Yes: Use Auto or Require — no custom CA needed.
→ No / unsure: Start with Auto. If it fails, check the error in section 7 above.

9 — Security best practices

Do
  • Use Auto as the default for any cloud or remote database.
  • Use Require for production sources where you want to guarantee encryption.
  • Supply the actual CA certificate when you get a CA verification error — don't downgrade to Off.
  • Rotate CA certificates before they expire and update the CA field in your data source settings.
  • Use a dedicated read-only database user for Claritect — never use a superuser or admin account.
Don't
  • Use Off for any database that holds real or sensitive data.
  • Set NODE_TLS_REJECT_UNAUTHORIZED=0 on the server.
  • Share CA certificates over unencrypted channels.
  • Paste your database user's password or private key into the CA field by mistake — it only accepts CA certificates.
  • Use Off as a permanent workaround for a corporate CA error — find and paste the correct CA instead.
