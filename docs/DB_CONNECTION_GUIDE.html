Database Connection Guide

This guide covers the four supported source types in the connection wizard: Postgres, MySQL, Snowflake, and BigQuery. The same product flow is used for all four: Source → Governance → Activate.

Postgres is live-tested end to end on the local stack. MySQL, Snowflake, and BigQuery are fully wired in code and covered by automated provider tests and UI validation.
For Snowflake specifically: the connector support is in place and should work with a valid account, database, schema, warehouse, and read permissions. I have not connected this local machine to a real Snowflake account, so treat it as implemented and test-covered, but not live warehouse-verified from this environment.

Connection Flow

Step What you do What Claritect does
Source Choose the database type, enter the connection string, test it, then connect. Validates the connector, inspects visible relations, and prepares governance.
Governance Select the tables to allowlist and click Save allowlist. Validates access and builds the governed catalog used by chat, planning, and reports.
Activate Run a safe query, confirm results, and submit the connection. Enforces read-only, SELECT-only execution and makes the source available to the product.

Provider Setup

Postgres

Expected connection string

postgresql://user:password@host:5432/database?sslmode=require

Notes

  • Also applies to Neon and similar Postgres-compatible read replicas.
  • If your server is local or non-SSL, use ?sslmode=disable.
  • If your TLS chain is custom, paste the CA certificate in Advanced TLS.

Minimum access

  • Read-only user
  • SELECT on the allowlisted tables/views
MySQL

Expected connection string

mysql://user:password@host:3306/database?sslmode=require

Notes

  • Use a dedicated read-only MySQL user if possible.
  • The product validates access first, then moves into governance and activation.
  • Prefer TLS with CA validation for production sources.

Minimum access

  • Read-only user
  • SELECT on the allowlisted tables/views
Snowflake

Expected connection string

snowflake://user:password@account/database/schema?warehouse=COMPUTE_WH

Required parts

  • Account in the host position
  • Database in the path
  • Schema in the path or query string
  • Warehouse in the query string

Minimum access

  • Role can use the warehouse
  • Role can use the database and schema
  • Role has SELECT on the allowlisted tables/views
BigQuery

Expected connection string

bigquery://project-id/dataset

Supported auth forms

  • credentials_json=...
  • credentials_base64=...
  • Application Default Credentials if the runtime already has them
  • key_filename=... if configured on the runtime host

Minimum access

  • roles/bigquery.dataViewer on the dataset
  • roles/bigquery.jobUser on the project

How To Connect Each Database

Postgres

  1. Go to Data Sources and click Connect new database.
  2. Select Postgres.
  3. Paste a Postgres connection string. Example: postgresql://reader:secret@db.company.com:5432/analytics?sslmode=require.
  4. Click Test connection.
  5. If the test passes, click Connect source.
  6. In Governance, select the tables you want on the allowlist and click Save allowlist.
  7. When the catalog modal completes, continue to Activate.
  8. Run the suggested safe query and then click Submit connection.

MySQL

  1. Select MySQL in Step A1.
  2. Paste a MySQL connection string. Example: mysql://reader:secret@mysql.company.com:3306/analytics?sslmode=require.
  3. Test the connection, then connect it.
  4. Choose the governed allowlist, save it, and wait for cataloging.
  5. Run a safe query in Activate and submit the source.

Snowflake

  1. Select Snowflake in Step A1.
  2. Paste a Snowflake connection string. Example: snowflake://reader:secret@acme/testdb/public?warehouse=COMPUTE_WH.
  3. Make sure the user’s role can use the warehouse, database, and schema, and can read the target tables.
  4. Test the connection. If it passes, connect the source.
  5. Pick the allowlisted tables, save governance, then continue through cataloging and activation.
  6. Run a safe query and submit the connection.

BigQuery

  1. Select BigQuery in Step A1.
  2. Paste a BigQuery connection string. Example: bigquery://demo-project/analytics.
  3. Make sure the runtime has valid credentials and the dataset/project IAM roles needed for reading and query execution. If you need advanced auth fields, use the manual connection string mode in the app.
  4. Test the connection, then connect the source.
  5. Choose the allowlist, save governance, allow cataloging to finish, then continue to Activate.
  6. Run a safe query and submit the source.

Corporate TLS / SSL Inspection

For a full reference — all three SSL modes, error message decoder, per-provider behaviour, and a quick decision guide — see the dedicated SSL / TLS Guide.

If you are on a corporate network and see TLS errors against a cloud database like Supabase, the most common cause is SSL inspection. Your company proxy or security appliance is presenting a corporate certificate to Node, and the API server does not trust that CA yet.

You usually do not need a special certificate from Supabase. What you need is your corporate root or intermediate CA.

Fastest path

  1. Ask IT or your security/network team for the PEM/CRT of the corporate TLS inspection CA.
  2. Open the file in a text editor.
  3. Copy everything from -----BEGIN CERTIFICATE----- through -----END CERTIFICATE-----.
  4. Paste it into Advanced TLS → Custom CA (PEM) in the connection wizard.
  5. Retry the connection with SSL mode still on Automatic or Require TLS.

If you need to find it on Windows yourself

  1. Open certmgr.msc for your user certificates, or certlm.msc for machine certificates.
  2. Check:
    • Trusted Root Certification Authorities → Certificates
    • Intermediate Certification Authorities → Certificates
  3. Look for your company or security vendor name, for example Zscaler, Netskope, Cisco Umbrella, Palo Alto, or your company name.
  4. Open the certificate and verify it looks like the corporate inspection/root CA.
  5. Export it as Base-64 encoded X.509 (.CER).
  6. Open the exported file in Notepad and copy the full certificate block.
  7. Paste that into Advanced TLS → Custom CA (PEM).

If you want to trust it for the server instead of per connection

  1. Save the CA PEM to a file on the API server.
  2. Set NODE_EXTRA_CA_CERTS=/path/to/your-corporate-ca.pem.
  3. Restart the API server.
Use sslmode=no-verify or the UI’s no-verify option only as a temporary dev workaround. The better fix is to trust the correct corporate CA.

Troubleshooting

Problem Likely cause What to change
SSL error on Postgres or MySQL The server does not support SSL, or your CA chain is custom. Use sslmode=disable for local/non-SSL dev only, or provide the CA certificate in Advanced TLS.
Snowflake says account or warehouse is missing The connection string is missing required Snowflake parts. Include account host, database, schema, and warehouse=....
Snowflake authenticates but governance finds nothing The role can connect but cannot see the intended database/schema/tables. Grant usage on warehouse, database, schema, and SELECT on target tables/views.
BigQuery says dataset is missing The dataset is not included in the path. Use bigquery://project-id/dataset or provide dataset=....
BigQuery authentication fails Credentials are missing or malformed. Provide valid credentials_json, credentials_base64, a valid key_filename, or runtime ADC.
Activation safe query fails The allowlist is too narrow or the source user lacks SELECT on one of the chosen relations. Adjust the allowlist or grants, then save governance again.
